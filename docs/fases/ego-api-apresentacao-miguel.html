1. Porquê agora

Hoje a base de dados é alimentada por um relatório do eGO descarregado por um browser automático (o scraper). Falha em silêncio quando o eGO muda alguma coisa:

  • 14 e 15/10: o eGO passou a pedir a escolha de escritório no login; dois dias de sync parados.
  • 27 e 28/10: 14 e 37 oportunidades recusadas por um estado novo («Criada») e 180 e 492 notas por gravar.
  • Os relatórios são enviados por email acima de ~1 000 linhas, e dependem de HTML e do browser.

A API do eGO devolve os mesmos dados em formato estruturado, com identificadores estáveis e filtros por data. Já a usamos para criar leads, para o estado das propostas, para as oportunidades apagadas e para os imóveis de todos os estados.

4. E a Web API dos imóveis?

Hoje há duas fontes de imóveis: a Web API pública (só os publicados, com cerca de 10 minutos de atraso) e a API do CRM (todos os estados, 227 campos, identificador de backoffice). A proposta é ficar só com a API do CRM.

Ganhamos

  • Uma só fonte, em vez de duas a reconciliar.
  • Todos os estados (hoje 705 imóveis só existem na API).
  • O identificador certo, que resolve os imóveis «invisíveis» e o detalhe por CRM em HTML.
  • O imóvel traz a lista de portais onde está publicado (portals).

A validar antes de desligar a Web API

  • Que o campo de portais equivale ao «publicado no site» (hoje decidido por disponivel_na_api).
  • Fotografias e características (FeatureTags: «há na zona» ≠ «o imóvel tem»).
  • Coordenadas só com o indicador de GPS verdadeiro.
  • Imóveis «publicados apesar de indisponíveis».

Plano: correr as duas em paralelo, comparar campo a campo durante uma semana e só então retirar a Web API. A página pública e as landing pages não mudam.

5. Plano de implementação

Fases por risco crescente, uma de cada vez. Cada uma corre em paralelo ao scraper atual (sem escrever em produção) e só o substitui quando os números batem.

A1

Cliente de leitura da API

Listas paginadas, lotes de identificadores, repetição em erro. Sem escritas. Testes com respostas simuladas.

A2

Notas (a que está partida hoje; só acrescenta)

Critério: notas da API contêm as da base; as 672 em falta aparecem. Precisa de uma coluna nova (identificador da nota).

A3

Tarefas

Critério: pendentes = API ±1 %. Decidir os estados «Cancelado», «Não aplicado» e «Arquivada».

A4

Visitas

Critério: API contém as 1 791 da base; explicar a diferença antes de gravar.

A5

Oportunidades (campos diretos, etapa, datas e estado da proposta)

Critério: zero linhas ignoradas; comparação linha a linha com o relatório durante uma semana. O valor da proposta fica à parte (decisão abaixo).

A6

Contactos, por incremento

Critério: identificador e telefone iguais aos do relatório nos alterados. A chave atual da tabela mantém-se (não mexer sem o Miguel).

A7

Imóveis: só a API do CRM (retira a Web API e o detalhe em HTML)

Critério: validações da secção 4; os 10 imóveis invisíveis deixam de falhar. Antes disto, fazer a 1.ª passagem dos 705 imóveis.

A8

Desligar o browser automático, o relatório e a Web API

Só depois de A2 a A7 estáveis durante um mês. Liberta memória no servidor do scraper.

O que não muda

  • O portal do Miguel continua a ler as mesmas tabelas: só se acrescentam colunas novas, vazias por omissão; nada se apaga.
  • Os assistentes continuam a não escrever em oportunidades.
  • Nunca se altera uma entidade no eGO (incidente de 14/10).
  • Dados pessoais (NIF, IBAN, data de nascimento): não se lêem nem guardam.

Riscos

  • A mesma conta do eGO. A API usa o utilizador do CRM. A password, que tinha aparecido numa saída de diagnóstico a 15/10, foi mudada a 28/10 e já está aplicada nas duas apps e testada. Falta só confirmar que nenhuma outra ferramenta (n8n, Make) usa esta conta com a password antiga.
  • Escrita em lote. Os campos esparsos da API podem apagar dados por engano; mantêm-se as regras de gravação linha a linha de hoje.
  • Limites do eGO (token de 24 h, proteção de acesso): contidos com cache e um cliente único.

6. Decisões para a reunião

  1. Começar pelas notas (A2)? Resolve o que está partido e não substitui nada.
  2. Valor da proposta: manter o relatório só para esta coluna, pedir o endpoint ao eGO ou aceitar vazio?
  3. Web API dos imóveis: de acordo em ficar só com a API do CRM, depois de uma semana de comparação?
  4. Tarefas legadas: limpar as ~3 400 pendentes antigas (listas «Ativas» e «Arquivadas» de há meses) e que fazer aos estados Cancelado, Não aplicado e Arquivada.
  5. Imóveis: autorizar a 1.ª passagem dos 705 imóveis que só existem no eGO (pedido #45).
